# claims-intake

A claims intake pipeline for the kind of data a health plan actually receives: a fixed-width batch file from a legacy claims system, a CSV export from a provider portal, and scanned claim forms (images and PDFs). Every claim, whatever channel it came through, is normalized, validated, de-duplicated and routed: accepted claims become FHIR R4B `Claim` resources, fixable problems go to a review queue, and claims that can never be valid are rejected. It runs as a Prefect flow, tracks extraction cost per document, and raises alerts on operational problems and on drift against a baseline run.

All data is synthetic: every member, provider and claim is generated by `claims_intake.synth`, and each form says so on its face.

## What it handles

| source | format | the awkward part |
|---|---|---|
| legacy batch | 80-character fixed-width records (header, claim, line, trailer) | implied-decimal amounts, `YYYYMMDD` dates, undotted ICD-10 codes; the trailer's control totals must match or the whole file is held |
| provider portal | CSV, one row per service line | US dates, `$1,234.00` amounts, `;`-separated diagnoses, claim fields repeated on every row (and checked to agree) |
| scanned forms | PNG, JPEG, PDF | Claude reads the form into a schema; anything it cannot read with confidence is flagged, not guessed |

Then, for every claim:

- **Validation**: NPI check digit (Luhn with the 80840 prefix), ICD-10-CM / CPT / HCPCS / modifier / place-of-service formats, member on the eligibility file and covered on the service date, service date not in the future or before birth, line charges adding up to the claim total, name and date of birth matching eligibility (accepting `LAST, FIRST`).
- **De-duplication by content**, not by the sender's claim id: the same visit resent through the portal with a new id is caught.
- **Routing**: no issue → accepted; anything a reviewer can fix from the document → review queue; not a member, not covered, future service, service before birth → rejected.
- **Idempotency**: files are tracked by SHA-256, so re-running over the same inbox changes nothing. A held batch can be corrected and resent.
- **FHIR output** for accepted claims, validated against the R4B model by `fhir.resources`. It references `Patient/{member_id}` and `Coverage/{member_id}`; no name or birth date goes into it.

## The sample run

`claims-intake synth` writes 2 legacy batches, 1 portal file and 6 scans with planted problems (`data/PLANTED.json`). One run:

| claim | outcome | why |
|---|---|---|
| L-1001, L-1002, L-1003, P-2001, S-3001, S-3002, S-3005, S-3006 | accepted | clean (S-3006's extraction fails once and succeeds on retry) |
| L-1004 | review | lines sum to $171.00, claim header says $181.00 |
| L-1006 | review | NPI check digit is wrong |
| P-2003 | review | diagnosis `11.9E` is not ICD-10-CM |
| P-2005 | review | the name was typed differently from eligibility |
| S-3003 | review | the birth date on the form is smudged; the extractor flags it |
| L-1005 | rejected | coverage ended Sept 30, service on Nov 7 |
| P-2004 | rejected | service date is in the future |
| P-2002 | duplicate | same visit as L-1001, resent through the portal |
| legacy_20261119.txt | held | trailer says 4 claims, the file has 3: none of its claims are loaded |
| scan_04.png | extraction failed | no NPI on the form |

That run raises three alerts: a held batch (critical), review rate 33% (above 30%), and 1 of 6 scans failed (above 10%).

## Review queue

```bash
claims-intake review list
#1    L-1004   legacy member M******11  issues: total_mismatch
#2    L-1006   legacy member M******85  issues: npi_invalid
#3    P-2003   portal member M******59  issues: dx_format
#4    P-2005   portal member M******33  issues: name_mismatch
#5    S-3003   scan   member M******44  issues: unclear_field
claims-intake review approve 5 --reviewer rn01 --set member_dob=1959-04-06
claims-intake review reject 2 --reviewer rn01 --note "asked provider to resubmit"
```

Listings mask the member id. A corrected claim is validated again before it can be approved, so a reviewer cannot approve a claim that still has an error; approval writes its FHIR resource.

## Keeping patient data in its place

- Issue messages, log lines, metric names and alert text are written without patient data in the first place.
- As a safety net, a scrubber replaces every member id, name, name part and birth date of the claims in flight (and anything shaped like a member id) with `[PHI]` in log lines, the metrics file and alert payloads.
- Prefect tasks that hold claims run with `persist_result=False` and no cache policy, so Prefect never writes claim contents to its result storage or hashes them into cache keys. Only paths and the PHI-free report cross into Prefect's state. (After a real run, the Prefect database and result storage were searched for member names and ids: no matches.)
- The review queue in SQLite does hold full claims: that is the one place a reviewer needs them.

A test runs the whole pipeline and searches the logs, metrics and alerts for every member id, name, last name and birth date in the eligibility file. None appear.

## Extraction, cost and retries

`ClaudeExtractor` sends the page as an image or PDF block and asks for an `ExtractedClaim` through structured outputs (`client.beta.messages.parse` with a Pydantic schema). Values come back exactly as printed and are parsed by the same code as the other sources. The prompt asks the model to list any field it is unsure of in `unclear_fields`, and those go to review. A refusal or truncated output counts as a failed extraction (still billed and counted); 429 and 5xx errors raise, so Prefect retries the task (3 retries with backoff and jitter); other 4xx errors do not retry. Server-side refusal fallback is enabled.

Default model `claude-opus-5-5` at low effort (transcription, not reasoning); `--model claude-sonnet-5-5` or `claude-haiku-5-5` are one flag away. Each run records tokens, cost per document (from list prices, in integer micro-dollars), and p50/p95 latency, and alerts if cost per scan passes $0.05.

`FakeExtractor` is an offline stand-in that returns the generator's answer key with simulated token counts. It tests everything around extraction (routing, retries, cost accounting); it says nothing about how well a model reads the forms. **The real extractor has not been run on these forms yet**; the cost figures in a fake run are simulated.

## Drift

Pass `--baseline` with the metrics file of a run you trust. The next run is compared on the claim-charge distribution (population stability index over charge buckets, alert above 0.2), review rate (alert if it rises more than 15 points), and issue codes that never appeared in the baseline (3 or more). Drift checks are skipped for runs with fewer than 10 claims, where they would be noise.

## Running it

```bash
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/claims-intake synth
.venv/bin/claims-intake run --today 2026-11-21            # offline extractor
.venv/bin/claims-intake run --extractor claude            # real extraction; needs Anthropic credentials, spends credits
.venv/bin/pytest
```

Outputs go to `out/`: `fhir/*.json`, `state.db` (files, claims, review queue), `metrics/<run>.json`, `alerts.jsonl`. `--webhook URL` also POSTs each alert; a webhook outage never fails the run.

Docker:

```bash
docker build -t claims-intake .
docker run --rm -v "$PWD/work:/work" claims-intake synth --out data
docker run --rm -v "$PWD/work:/work" claims-intake run --today 2026-11-21
```

The image runs as a non-root user and has no data in it; inputs and outputs are on the mounted volume.

## How it was tested

- **101 pytest tests**: each source format and its failure modes (bad record length, line for an unknown claim, record after the trailer, missing trailer, rows of one claim that disagree), every validation rule, routing, de-duplication across channels, the Claude extractor against a stub client (request shape, PDF vs image, refusal, truncation, 429/5xx retry vs 4xx no-retry, cost), FHIR validity, the scrubber and log filter, PSI and every alert rule, the whole pipeline over the sample (every claim's decision, held batch, idempotent rerun, resent fixed batch, cross-file duplicate, review approve/reject through the CLI), the PHI leak search, and the Prefect flow itself on a throwaway Prefect server, including the retry and what happens when retries run out.
- **Mutation check**: 13 deliberate bugs (NPI check digit ignored, trailer count not checked, ineligible member sent to review instead of rejected, dedupe keyed on claim id, scrubber missing member-id shapes, held batch still loaded, FHIR total from the first line, unclear fields not flagged, PSI sign flipped, files never marked seen, refusal not detected, implied decimals read as dollars, line sum not checked). All 13 caught.
- Tests found one real gap while writing them: names in `LAST, FIRST` order were flagged as mismatches.
- CI runs ruff and pytest on Python 3.12, 3.13 and 3.14, builds the Docker image, and runs the flow inside the container, checking the outcome counts. Docker is not installed on the machine this was written on, so the container path has only run in CI.

## Limits

- Format checks only: codes are not checked against the licensed CPT or ICD-10-CM code sets, NPIs are not looked up in NPPES, and there are no payer edits (NCCI, medical necessity).
- The legacy format is a simplified layout of my own, not X12 837. A real 837 feed needs an EDI parser.
- One process, one SQLite file. A production version would put state in Postgres and run the flow on a Prefect worker, with the review queue behind access control and an audit trail.
- No HIPAA controls beyond the PHI handling above (no encryption at rest, access control or BAA-covered infrastructure).
